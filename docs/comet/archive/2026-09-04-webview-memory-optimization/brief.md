# 目标
全面优化 ClipOne 的 WebView2 与主程序内存占用，在确保唤起流畅、无感延迟的前提下，将静默常驻物理内存从 400MB+ 压降至数十兆乃至个位数兆级别，并消除超大剪贴板内容在跨进程传输与前端渲染中的内存膨胀。

# 范围
- `Program.cs`：
  - 精细化优化 Chromium/WebView2 启动参数（限制单渲染进程、约束缓存池、禁用无用服务）。
  - 引入后台静默时的自动内存修剪机制（防抖触发 EmptyWorkingSet 与 GC）。
  - 改造 Web 消息处理，支持基于条目 Id 的单项与批量粘贴、写入剪贴板。
- `service/StorageService.cs`：
  - 提供 `GetClipById` 与批量查询接口。
  - 对推送给 Web 端的列表数据进行大文本截断保护，避免超大字符串涌入 Webview。
- `html/js/main.js`：
  - 列表按需分批渲染（首屏 25 条，滚动/按键越界追加），降低 DOM 节点数与图片显存。
  - 前端触发粘贴/复制时仅向 C# 发送 Id，杜绝大对象跨进程 JSON 序列化往返。
  - 窗口隐藏时主动触发 V8 堆内存回收。

# 非目标
- 不更换 Photino.NET 基础架构或引入 WPF / WinUI 等重型原生 UI 框架。
- 不缩减用户可保存的最大历史记录数（保持 300 条）。
- 不破坏现有的快捷键响应、多选粘贴、范围粘贴、即时搜索、托盘菜单与皮肤切换功能。

# 验收示例
- Scenario: 后台静默时自动修剪进程工作集内存
  - GIVEN ClipOne 与 WebView2 正在运行且窗口处于隐藏状态
  - WHEN 窗口隐藏超过空闲延迟阈值（如 3 秒）
  - THEN ClipOne 主进程及关联的 msedgewebview2.exe 进程物理工作集内存（Working Set）被自动修剪，总物理内存占用大幅下降至 30MB 以下，且按快捷键唤出窗口时仍能毫秒级即时展示且无白屏或闪烁
- Scenario: 前端列表按需分批渲染
  - GIVEN 剪贴板历史中存在多条记录（最多 300 条）
  - WHEN 用户打开剪贴板窗口或搜索过滤
  - THEN 前端优先渲染可见视口及首屏条目（如 25 条），随滚动接近底部时自动追加渲染后续条目，避免一次性生成上千个 DOM 节点与显存纹理
- Scenario: 粘贴与设置剪贴板基于 ID 交互
  - GIVEN 用户在前端选中某条历史记录并触发粘贴或复制
  - WHEN 前端向 C# 宿主发送 IPC 消息
  - THEN 前端仅发送条目 Id，C# 宿主根据 Id 从本地存储中检索完整数据并写入系统剪贴板，彻底杜绝大文本在 IPC 与 V8 堆中的全量序列化往返

# 约束与不变量
- 必须保持 Native AOT 与 `System.Text.Json` Source Generator 兼容性。
- 保证快捷键唤起速度与流畅度不受任何负面影响。

# 决策
- 决策 1: 内存修剪采用“隐藏后 3 秒防抖延时”策略，唤出时立即取消待执行的修剪，兼顾连续操作时的平滑度与长期静默时的极致低内存。
- 决策 2: 保留唤起不黑屏的必要 Chromium 参数（如 `--disable-background-timer-throttling`），同时补充单渲染进程约束、缓存池限制（10MB）、关闭翻译/更新/语音等不必要特性。
- 决策 3: 前端仅传输和缓存用于展示和搜索的数据，执行粘贴时向 C# 传输 ID，由 C# 本地获取原版完整内容。
